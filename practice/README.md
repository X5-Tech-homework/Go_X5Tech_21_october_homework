# Практика занятия 5

Развиваем сервис уведомлений из урока 4. Основная работа находится в `tasks.go`. Старые методы уже работают как в прошлом уроке, новые функции пока содержат заготовки.

## Что остаётся от предыдущего занятия

`Notifier`, `BaseNotifier`, `EmailNotifier`, `PushNotifier`, поля `Address`, `DeviceID`, `Messages`, функции `EmailAddress` и `Describe`. Указатели нужны потому, что `Send` меняет историю конкретного экземпляра.

`EmailAddress` и `Describe` сохраняют старое поведение, включая обработку nil. Во все функции отправки передаются корректные ненулевые реализации `Notifier`. Поддержка nil-каналов и typed nil при отправке в задание не входит.

Имя канала берётся через готовую функцию `channelName`. Она проверяет небольшой дополнительный интерфейс с методом `Name`, который есть у `BaseNotifier` и доступен через встраивание. Для реализации только с методом `Send` подписью будет имя её типа. Добавлять `Name` в `Notifier` не нужно.

## Шаг 1. Известная ошибка, первые 10 минут

1. Инициализируйте `ErrEmptyMessage` один раз через `errors.New`, текст: `пустое сообщение`.
2. В начале обоих `Send` проверяйте `message == ""`. Возвращайте именно `ErrEmptyMessage`.
3. При ошибке не добавляйте запись и не очищайте прежние сообщения.
4. При успехе сохраните поведение урока 4: добавить `n.Label(message)` и вернуть `nil`.

Пустой считается только строка `""`. Строка `" "` допустима, обрезать пробелы не нужно. Повторная отправка дописывает запись. Разные экземпляры сохраняют отдельные истории.

```bash
go test -v . -run TestStep1
```

## Шаг 2. Контекст и причина, следующие 10 минут

В `Dispatch` последовательно вызовите `Send` каждого канала ровно один раз с исходным сообщением. При первой ошибке остановитесь и верните обёртку формата `канал <имя>: <исходная ошибка>`. Используйте `channelName(n)` и `%w`.

Последующие каналы после ошибки не вызываются. Если ошибок нет, верните `nil`. Для nil-слайса и пустого слайса тоже возвращайте `nil`, даже если текст пуст: проверка сообщения находится в канале, а каналов здесь нет.

На вызывающей стороне причина должна находиться через `errors.Is` после нескольких обёрток. Если внутри был `*SendError`, его должен находить `errors.As`. Сравнение текста ошибки для выбора поведения не используйте.

```bash
go test -v ./practice -run TestStep2
```

## Шаг 3. Паника одного канала, последние 10 минут

`BrokenNotifier` уже дан: его `Send` намеренно паникует. `ErrNotifierPanic` тоже уже создана.

Реализуйте `SafeSend(n Notifier, message string) (err error)`:

- вызовите `Send` один раз;
- обычный результат верните без изменений, включая тот же объект обычной ошибки;
- внутри отложенной функции вызовите `recover` напрямую;
- при панике верните ненулевую ошибку, которая сохраняет `ErrNotifierPanic` через `%w` и содержит значение паники как текст через `%v`.

`panic` может получить строку, число или другое значение. Не приводите результат `recover` к `error` без проверки. `panic(nil)` при стандартном поведении Go 1.22+ тоже должен стать ошибкой. Обрабатывать причины внутри значения `panic(error)` через `errors.Is` не требуется: в этом упражнении причиной считается `ErrNotifierPanic`, а содержимое паники добавляется для диагностики.

Реализуйте `SafeDispatch(all []Notifier, message string) []error`:

- вызовите `SafeSend` для каждого канала по порядку;
- после обычной ошибки и после паники переходите к следующему каналу;
- каждую ошибку оберните контекстом `канал <имя>: ...` через `%w`;
- верните все ошибки в порядке каналов, без элементов `nil`;
- при полном успехе или пустом списке длина результата должна быть нулевой. Допустимы nil-слайс и пустой слайс.

Здесь `[]error` читается как «слайс ошибок». Пользуемся знакомыми `range` и `append`. Вызывающий код проверяет каждую ошибку отдельно. `errors.Is` принимает одну ошибку, а не весь слайс.

```bash
go test -v ./practice -run TestStep3
```

Проверка должна подтвердить, что после `BrokenNotifier` следующий `PushNotifier` сохранил сообщение. Одного сообщения «паника поймана» недостаточно.
